# Prevention plan: the plan card and the warning card (UI_PLAN.md slices 2 and 3)

Status: research, 2026-10-08. For review before slice 3 is built. Covers VISION.md 3.1 (check before editing) and 3.2 (pause in the middle).

## 1. One mechanism for every provider: `team_plan` holds the call

All six providers already mount T3's own MCP server (`t3-code`; ClaudeAdapter, CodexAdapter, CursorAdapter, GrokAdapter, OpenCodeAdapter, AntigravityAdapter), and the team tools live there. So the stop does not need six integrations:

1. Before its first edit, the agent calls `team_plan` with the files it expects to change (slice 2, built in the commit after this plan: it claims them, and the card shows each file's holder).
2. Slice 3: if a planned file is held by someone else, the server **does not answer yet**. It appends a `team.choice` activity to the thread (the inline card with the choices) and waits on a `Deferred`, the way the preview tools already wait for the browser (`PreviewAutomationBroker`).
3. The click sends a new WebSocket command; the server records the choice on the card (so it stays in the thread) and resolves the `Deferred`. The tool returns the choice and what to do, for example "User chose: find another way. Do not change src/auth/login.ts; call team_plan again with the new plan."

Why not the existing pieces: approvals and `user-input.requested` (`ComposerPendingUserInputPanel`) are requests that a provider makes, with ids and answers routed back to that provider's adapter; T3 cannot raise one itself. They also show above the composer, not in the message (design pick C), and a choice here has side effects (switch branch, send a question). MCP elicitation is uneven: Codex shows it (`mcp_elicitation_approval`), the Claude SDK declines it because T3 sets no `onElicitation`, and ACP agents and OpenCode are unknown. We reuse the patterns (an activity on the thread plus a respond command), not the panels.

### How long each provider can wait, and the fallback

| OpenCode                  | Short only. **Fallback, the same card with a different delivery:** the server holds the call up to a per-provider cap (Codex and Claude 55 min, others 45 s). At the cap it answers: "Paused: the user has not chosen. Do not edit these files. End your turn now; the choice comes as the next message." When the user clicks, a held call gets the answer; with none (cap reached, server restarted, app closed), T3 starts a normal turn whose message is the choice (`thread.turn.start`). This path also covers "Wait", which can take days. Risk: an agent that ignores "end your turn". The guard in section 3 catches its edits.

## 2. What each choice does in the code

- **Wait (team and solo).** The card records `waitingFor` (the holder's claim id and paths) and the turn ends. A small reactor watches the team state the poller already loads. A claim is released when its thread's pull request merges, or when the thread is archived (`TeamClaimAutoRelease`, on the holder's server). The reactor sees the release on the next poll (10 to 20 s), then fetches `origin`. A thread with no edits yet moves its worktree to the new `origin/<base>`; one with edits rebases, and stops to tell the user on a conflict. Then it starts a turn: "Yassine's work on src/auth is merged; you are on top of it. Continue the task." Solo: "Wait for that chat" fires when the other chat's claim is released.
- **Build on top (team only).** The holder's branch must be known: claims get an optional `branch` (the claiming thread's branch, pushed with the writer file; old files without it still read). The server runs `git fetch origin <branch>`, then switches this thread's worktree to a new branch from it. If the holder never pushed, the choice is shown but disabled, with "not pushed yet". The tool returns "You are on top of Yassine's unmerged work; read their changes before editing."
- **Ask (team only; solo has no ask).** The asker's writer file gets `questions: [{ id, to, paths, text, thread }]`; the holder's server reads it on the next poll and shows it in the presence chip popover and on the holder's thread that holds those paths. The holder answers on any of their clients (web, desktop, phone: the phone talks to the holder's own server). The answer goes into the holder's writer file (`answers: [{ questionId, yes, text }]`). The asker's server reads it and delivers it like a choice: "yes" continues as "go anyway, agreed", and "no" shows the card again without Ask. No answer: the card says "asked 2 h ago" and the other choices stay open.
- **Find another way.** Releases this thread's claims on the held files and returns "Do the task without changing these files: … Call team_plan again with your new plan." The next plan card shows the new plan.
- **Go anyway.** The claims stay as they are (overlapping claims are already allowed). An activity line goes to the team state ("Mouhssine went ahead on login.ts, held by Yassine"). The holder's agent gets it as a `lateOverlaps` entry on its next team tool call (exists, each told once), and the holder's thread shows the overlap mark (slice 1). Both people are warned; step 5 (merging help) uses it later.

## 3. The pause in the middle (VISION.md 3.2)

Trigger: an edit to a file that **another thread holds** and that **this thread does not hold** (its plan and later claims). Files nobody holds are never stopped. The check is one pure function, `heldElsewhere(path, thread, state)`, shared by every provider. It answers with the same card, through `team_plan` (the agent is told to plan the new file), so there is one card and one set of choices.

| Provider     | Where T3 sees the edit before it lands                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Sure?                          |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| Claude       | A `PreToolUse` hook passed in the SDK options (an in-process callback; hooks run in `bypassPermissions` too) on `Edit`, `Write`, `MultiEdit` and `NotebookEdit`. It answers `deny` with the reason "held by Yassine: call team_plan with this file first".                                                                                                                                                                                                                                            | High                           |
| Antigravity  | Its writes already go through T3 (`clientFileSystem: true`, `handleWriteTextFile`): T3 refuses the write with the same reason.                                                                                                                                                                                                                                                                                                                                                                        | High                           |
| Codex        | With approvals on, `applyPatch` approval requests carry the paths: T3 checks them first. In full access (the default), Codex sends none. Codex 0.160 has `preToolUse` hooks with an `mcp_tool` handler that could call our server, but whether hooks passed with `-c` need the user to trust them is unknown: spike first. Fallback: the `fileChange` item arrives, T3 interrupts the turn (`turn/interrupt`) and shows the card; the edit is already on disk, and the turn's checkpoint can undo it. | Medium (hook), High (fallback) |
| Cursor, Grok | ACP permission requests reach T3 even in full access (T3 auto-approves them): check the tool call's `locations` before approving. If an agent edits without asking, T3 falls back to interrupt-after, as for Codex.                                                                                                                                                                                                                                                                                   | Medium                         |
| OpenCode     | T3 writes the session's permission rules (`opencodeRuntime.ts`): add `edit` rules set to `ask` for held paths, then check `permission.asked`. The rules must change when claims change.                                                                                                                                                                                                                                                                                                               | Medium                         |

Not caught anywhere: edits made through shell commands (`sed`, scripts). The plan and the interrupt-after path still see them in the turn's diff.

## 4. What can be tested automatically, and what needs a live run

Automatic (no provider): `team_plan` claims, holders and the activity (slice 2, done); the hold and its delivery (a held call resolved by the respond command; at the cap, the fallback text; a click with no held call starts a turn); `heldElsewhere`; the Claude hook callback called directly; the Codex approval check; the Antigravity write refusal; Ask and Wait across two `GitTeamService`s on a `file://` origin (as the existing two-person tests do); timeline logic (the card stays visible after its turn folds).

Live only: whether each real model calls `team_plan` before editing and obeys "end your turn"; Codex with the raised `tool_timeout_sec`; Codex hook trust; whether Cursor and Grok ask before editing in full access; OpenCode rule updates; answering Ask from the phone; a two-person run on GitHub (now with a second gh account, WORKING_RULES.md).

## 5. What I would build first

1. **Slice 3a:** the hold in `team_plan`, the choice card, "Find another way" and "Go anyway", the fallback delivery, and Codex's `tool_timeout_sec`. Solo and team; no new team-state fields.
2. **Slice 3b:** the guard: Claude's hook and Antigravity's write refusal (both high confidence), then the interrupt-after path for the rest.
3. **Slice 3c:** "Wait" (solo first: the other chat's release).
4. **Slice 3d:** "Ask" (writer-file `questions` and `answers`), then "Build on top" (claim `branch`).

Open question for you: slice 2's `team_plan` claims every planned file, held ones included (as `team_claim` does today), so the holder sees an overlap mark while you decide. The other way: claim only free files until you pick "Go anyway". I would keep claiming all of them, because the holder learns early, and "Find another way" releases them.
