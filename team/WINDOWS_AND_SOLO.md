# Native Windows and solo use: audit and test plan

Status: research only, 2026-10-07. Nothing here is fixed yet except item W1 (fixed in a3f67847a). Written for VISION.md section 6, requirements 3 (great solo) and 5 (native Windows).

How sure each finding is:

- **Seen**: read in our code, the failure follows from it.
- **Likely**: how Windows or Git for Windows behaves, as I know it; not run here (this laptop runs the code in WSL).
- **Guess**: worth checking, could be fine.

Nothing below was run on native Windows. Upstream says so too: `.github/workflows/windows-tests.yml` notes that "nothing in the suite passes on Windows yet".

## 1. The short list

The five to fix or check first, most important first:

1. **W2. Git Credential Manager popping a sign-in window from a background push.** A poller push every 15 s can open a browser window nobody asked for.
2. **W1/W3. Slow disks and antivirus make Git calls slow.** W1 (teammates vanish on a slow read) is fixed; reads are still one process per file, and the 10 s limit can still trip.
3. **W5. Path case.** Windows paths are not case-sensitive, our overlap check is. Two people (or an agent) writing `src/Auth` and `src/auth` get no warning.
4. **S1. Solo needs GitHub.** Without a GitHub remote and `gh` signed in, none of the team layer works, so solo users get nothing.
5. **W9. The glass and the title bar on Windows 11.** Untested; it decides whether the design in DESIGN_DIRECTION.md works on Windows at all.

## 3. W1, W3 and slow disks

The bug fixed in step 1 is the clearest case of a wider Windows risk: **we treated "Git was slow" like "Git said no"**. On Linux in WSL, Git calls in the state repo take a few milliseconds. On native Windows each one starts a new process, and Defender scans `git.exe` and files under `.git` as they are opened; a laptop hard drive waking up, or a full scan running, can add seconds. The state repo is read after every fetch and sync, by up to 12 processes at a time (W3), each with a 10 s limit.

What happens now when a call is too slow:

- Reading the state: the last state is kept and `team_status` says it is not fresh (W1, fixed).
- Fetch or push: counted as "unreachable", the same as offline. The write stays on this computer and the poller pushes it later (backing off to at most 15 minutes). Correct, but a slow disk then looks like a bad network.
- Saving this server's own file (`saveMine`): fails the tool call (W10).

What would make it robust: fewer processes per read (W3), retrying renames (W10), and logging how long Git calls take on Windows so a slow-disk report can be told apart from a network one. Excluding T3 home from Defender would help too, but we should not ask users to do that.

## 4. Solo today

### What works solo today

Only in a "team of one": a project with a GitHub remote, `gh` signed in with push access, and `t3 team init` run. Then:

- Claims and overlap warnings between your own parallel chats (claims are per chat, and `team_claim` reports overlaps with any other chat, yours included).
- Handoff notes and automatic notes, `team_memory_search` with freshness marks (fresh, maybe outdated, not merged yet).
- The first-turn briefing, `team_status` (now with `notFresh`), tasks.
- Claims released when a chat is archived.

## 5. Test plan on your Windows laptop (installer step, VISION.md step 6)

Goal: the real installed app, native Windows (not WSL), from a clean user, through the team flows. About two hours. I prepare scripts and a checklist; you click.

**0. Before.** A Windows 11 laptop (note the build: `winver`, 22H2 = 22621 or later for Mica). A second Windows user account or a fresh machine is best, so nothing from WSL leaks in. Have a private scratch repo on GitHub you can push to.

**1. Build the installer.** On the laptop in PowerShell (not WSL): Node 24 (`package.json` engines), Git for Windows, Vite+; clone to a short path (`C:\src\t3code`), `vp i`, `vp run dist:desktop:win:x64`. If the local build fails, use the fork's own GitHub Actions on `windows-latest` (upstream's runner is a paid Blacksmith one) and download the artifact. Write down every step that needed a fix; that list is the contributor guide.

**2. Team tests on Windows CI.** Before the laptop session: fix W15 (`pathToFileURL`) and run `vp test run src/team/ src/mcp/toolkits/team/ src/cli/team.test.ts` on a `windows-latest` runner in our fork. Every failure is a finding.

**3. Install as a new user.** Run the NSIS installer. Record: SmartScreen (W17), install folder, Start menu entry, first launch time. Do not install `gh` yet.

**4. No gh, then gh.** Open the scratch repo: the app should say gh is missing, plainly. Install gh with winget while the app runs: does the app see it (W4)? Restart, `gh auth login`, open again.

**5. Two people, one laptop, native.** Clone the scratch repo twice (`C:\src\scratch-a`, `C:\src\scratch-b`), run the installed app on one and a WSL or second-account server on the other, as in slice 8. Check: claim, task, handoff each way; the same-second race; the file-overlap warning. Time each sync with the Git-log script from slice 8. Also time 20 state reads (W3); then repeat during a Defender quick scan (W1, slow disk).

**6. Credential and paths.** Sign out of GCM (`git credential-manager erase` for github.com), make a claim: does a window pop up (W2)? Claim `src/Auth/x.ts` in one chat and `src/auth/x.ts` in another (W5). Open the project once as `C:\src\scratch-a` and once as `c:\src\scratch-a` (W8). Put a project on a USB stick formatted exFAT (W6). Make a project with a deep folder and start a worktree chat (W7).

**7. Glass check.** A small Electron script (I will write it) opening a window with `backgroundMaterial: "mica"` and T3's title bar settings: maximized, snapped, inactive, light and dark, transparency effects on and off (W9). Screenshots to `test-screenshots`.

**8. Solo.** A fresh folder with no remote: what the user sees today (S1). That is the "before" picture for local-only mode.

**9. Uninstall and reinstall.** Data in `%USERPROFILE%\.t3` should survive; check `icacls` on the secrets folder (W11).

Results go into PROGRESS.md and this file (each W item marked confirmed, fine, or fixed), screenshots into `test-screenshots`.
